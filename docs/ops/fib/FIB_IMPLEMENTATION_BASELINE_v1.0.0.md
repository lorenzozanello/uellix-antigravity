This is a **candidate** baseline. It does not open implementation, does not activate document grounding, and does not freeze Stella Pilot Core. ## 2. Architecture Invariants

These hold across every contract, database object, and implementation unit in this baseline and are not restated per-item unless an item narrows or extends one:

1. **Evolutionary, not a rebuild.** The measured repository is structurally closer to the frozen authorities than a from-scratch design would assume. Governance state is already modeled as separate append-only objects beside immutable payload (`sroi_run_reviews` beside `sroi_calculation_runs`); `db/migrations/0030_immutability.sql` already installs append-only triggers on `audit_logs`, `sroi_calculation_runs`, `sroi_calculation_line_items`; Stella's hardest invariants (`requires_human_review = z.literal(true)`, the `UNTRUSTED_PROJECT_DATA` envelope, fail-closed source-index resolution, transactional audit-before-delivery, no auto-persistence, no authoritative SROI computation) are already structural; Portfolio arithmetic is already Σ/Σ via decimal.js. This baseline extends and completes what exists; it does not discard working architecture.
2. **No fabricated history.** No default, inference, reconstruction, or retroactive decision may complete a historical gap and be presented as a past fact. Every backfill class in §4 is either derivable from an already-persisted fact, or is declared `BACKFILL_NOT_REQUIRED`/`BACKFILL_IMPOSSIBLE`/`IMPOSSIBLE_TO_BACKFILL` and left permanently NULL or unmarked. `LEGACY_SPECULATIVE_BACKFILLS = 0` is a standing invariant of every migration this baseline authorizes, not merely a count at freeze time.
3. **Fail-closed over silent degradation.** Every gate in this baseline that can be evaluated as unresolvable resolves to "not eligible", never to a default pass. An operation whose durable record cannot be persisted does not complete; a DELETE that used to silently drop zero rows must fail explicitly instead.
4. **Append-only protections are never suspended.** No migration, hardening stage, or unit in this baseline recreates, disables, or bypasses the append-only/immutability triggers already applied to runs, calculation line items, or audit logs, or the new ones this baseline adds.
5. **Stella proposes; the system controls and calculates; humans decide and approve.** No unit in this baseline grants Stella authority to compute the authoritative SROI, approve, certify, or audit, or to satisfy human review by proxy. Omission or unavailability of Stella (V-17) never by itself degrades a result to preliminary, invalid, or methodologically inferior, and never blocks approval or lock.
6. **`db/19` (document grounding) stays dormant.** No unit, migration, or Stella change in this baseline imports, activates, or depends on anything gated behind `STELLA_GROUNDED_QUERY_ENABLED`. G5 is unresolved and explicitly outside this baseline's scope.
7. **One track per logical object.** Every database object in §4 is assigned to exactly one source-of-truth track (Drizzle or the externally-gated `db/prepared/` G2 track per `docs/21_DB_OBJECT_SOURCE_OF_TRUTH_ADR.md`); no logical object is created independently by both.
8. **Deploy-safety is orthogonal to backfill class.** The six migration stages in §6 (A–F) govern *when* a change is safe to ship; the backfill class recorded per item in §4 governs *what may be written* during backfill. A `SCHEMA_ONLY`-flavored item can still be behaviorally dangerous (e.g. a DELETE-rejecting trigger) and is staged accordingly — never assumed safe for the additive stage merely because it changes no data.

### C. Proxy intelligence & governance

**FIBC-010 — Proxy Provenance & Reproducibility**
AUTH: V-12. TARGET: to reach `approved` a proxy version must record value, unit, currency, reference year, geographic/contextual scope, linked outcome, identifiable source, consultation date where relevant, and a **recoverable reference** (URL/DOI/dataset id/linked document), plus relevance justification and documented transformations (FX, inflation, PPP, temporal/geographic/methodological adaptation). **FIBC-011 — `PROXY_DEFENDIBILITY_RUBRIC_v1.0.0`**
AUTH: V-32, NPDD-02. Confidence factors `C1_source_quality_verifiability`, `C2_outcome_correspondence`, `C3_stakeholder_population_fit`, `C4_geographic_context_fit`, `C5_temporal_fit`, `C6_methodological_unit_comparability`, each scored `0..3` (`insufficient|weak|adequate|strong`). `confidence_score = round(100 × Σ(C1..C6) / 18)`; base class `high ≥80`, `medium ≥60`, `low <60`. Ceilings: any factor `=0` caps the class at `medium`; `C1=0` **or** `C2=0` forces `low`. Risk factors `R1_provenance_risk`, `R2_source_limitation_risk`, `R3_conceptual_fit_risk`, `R4_geographic_population_transfer_risk`, `R5_temporal_obsolescence_risk`, `R6_transformation_risk`, `R7_methodological_uncertainty_risk`, each `0..3` (`negligible|limited|material|high`). `methodological_risk_score = round(100 × Σ(R1..R7) / 21)`; base `low <25`, `medium ≥25`, `high ≥50`. Floors: any factor `=2` ⇒ at least `medium`; any `=3` ⇒ `high`. Ratings are human with rationale and references; the derived classifications are **system-derived and not directly editable** — a level contradicting a ceiling or floor is rejected, never silently corrected. FC: any unrated factor blocks approval. Confidence and risk are independent, never inverses. A resulting `low` confidence or `high` risk requires a single explicit human exceptional-defendibility determination addressing both when both apply; otherwise the proxy is not approved and the outcome follows V-15. An approved `low`/`high` propagates to review, readiness (as an informative condition, never manual points), sensitivity, report limitations, and the snapshot. DB: FIBDB-006, FIBDB-044. OWNING UNIT: FIBIU-09.

Non-material = typographical/format/visual/ordering/internal-administrative only; **ambiguous ⇒ material** (fail-closed). Audit/approval metadata are never "editable non-material". ### H. Readiness — `SROI_READINESS_MODEL_v1.0.0`

**FIBC-021 — Readiness Model**
AUTH: NPDD-01, V-22, NPDD-03. The ten canonical dimensions are those enumerated at `docs/16_SROI_METHODOLOGY_SPEC.md:144-154`, which NPDD-01 promotes from *suggested* to canonical: D1 Narrative completeness · D2 Outcome quality · D3 Indicator quality · D4 Evidence coverage · D5 Proxy robustness · D6 Filter justification · D7 Calculation transparency · D8 Methodological risks · D9 Documentary traceability · D10 Versioning and audit trail.

Scoring, exactly as frozen: each dimension weighs **10%**; `dimension_score = 100 × applicable criteria satisfied / applicable criteria total`; every criterion weighs equally within its dimension; `global = arithmetic mean of the ten dimension scores`, scale `0–100`; bands `0–39 / 40–69 / 70–84 / 85–100`.

A governed `not_applicable` **satisfies** its criterion (NPDD-01: "podrá satisfacer el criterio correspondiente") and therefore stays in both numerator and denominator — it is only valid when established through governed state, decision, and rationale, never automatic and never set by Stella.

**D8-4 resolution by vacuity (frozen, final).** Exactly one of the 46 criteria depends on Stella: D8-4, "every open Stella `high` finding has human disposition." Resolving it as unsatisfied when Stella was never executed would make Stella indirectly mandatory for a high readiness score, contradicting V-17. The deterministic, three-state resolution:

| Situation | Resolution | Numerator | Denominator |
| --- | --- | --- | --- |
| Stella not executed for this run | **Satisfied by vacuity** — no findings exist, so "every high finding is disposed" is vacuously true | counts | counts |
| Stella executed, zero `high` findings | **Satisfied by vacuity** | counts | counts |
| Stella executed, all `high` findings disposed | **Satisfied** | counts | counts |
| Stella executed, ≥1 `high` finding undisposed | **Not satisfied** | does not count | counts |

Resolution-by-vacuity is automatic and deterministic, **not** a governed `not_applicable` — using the governed mechanism here would force a human to declare something about a tool they chose not to use, reintroducing the burden V-17 forbids. The governed `not_applicable` mechanism is reserved for criteria whose inapplicability is a genuine methodological determination (e.g. D1-4 causal chain when an outcome is out of scope, D3-4 quantity when an indicator does not monetize, D5-6 exceptional determination when confidence/risk are not `low`/`high`). No criterion of the 46 may resolve by consulting whether Stella is enabled, available, or was invoked — this is a construction invariant, verifiable by test. The Stella-omission record (FIBC-026, V-17) is traceability, not a readiness criterion, and never enters the matrix.

INVARIANTS: readiness never gates approval; no numeric threshold; a high score never compensates a failed gate; no human or Stella may inject points. Each run snapshots the global score, the ten dimensional scores, the criterion detail, and `readiness_model_version`. Portfolio may present descriptive readiness statistics with coverage, kept separate from the authoritative portfolio SROI.

**FIBC-044 — Outcome vs Impact Semantics**

**FIBDB-054** — `taxonomy_catalogs`, `taxonomy_codes` — external-reference identity sealing, NEW_CONSTRAINT + NEW_TRIGGER. AUTH: F-13, NPDD-03. CONTRACT: FIBC-043, FIBC-042. **Final normalized design (frozen at R4, superseding R2's and R3's column-duplication designs).**

**Measured evidence governing this design:** the relational chain `outcome_taxonomy_mappings.taxonomy_code_id → taxonomy_codes.id` and `taxonomy_codes.catalog_id → taxonomy_catalogs.id` is complete today with all three links `NOT NULL`; `taxonomy_catalogs.version` is already `NOT NULL` (`db/schema.ts:548`); the only writers of either reference table are `scripts/seed-taxonomies.ts` (lines 42, 48, 66, 71) — no product path writes catalogs or codes; `lib/taxonomies/service.ts:100-123` already resolves through both joins and merely omits `version` from its `SELECT`. Given this, `taxonomy_code_id` alone, once the referenced rows are sealed against mutation, **deterministically and permanently** resolves to exactly one `(catalog, version, code)` triple — there is exactly one path, so there is no second fact with which a mapping could disagree.

**Why the earlier column-duplication designs are superseded (not carried forward):** R2/R3 proposed adding `outcome_taxonomy_mappings.taxonomy_catalog_id` and `.taxonomy_catalog_version`, fixed at mapping-creation time. This has two defects the final design dissolves rather than patches: (a) a composite FK against `(catalogs.id, catalogs.version)` is not materializable as specified — PostgreSQL requires the referenced columns be covered by a unique constraint, and `id` alone is already the primary key, so expressing it would require a redundant `UNIQUE(id, version)`, a consistency trigger, or a service-level invariant, none of which R2/R3 resolved; and (b) persisting three separate facts (code, catalog, version) on the mapping creates a structural risk of the code pointing at catalog A while the mapping declares catalog B. **Retiring the two columns eliminates both defects at once**, at the cost of nothing: no current query needs catalog/version duplicated on the mapping (evidence above), and the resulting invariant is stronger than a constraint — a mismatch is not forbidden, it is unrepresentable, because the second field to disagree with does not exist.

**TARGET_COLUMNS_OR_FIELDS:**
- `taxonomy_catalogs`: replace `taxonomy_catalogs_code_unique(code)` with **`taxonomy_catalogs_code_version_unique(code, version)`**
- `taxonomy_catalogs`: trigger rejecting `UPDATE` of `code` and `version`, and rejecting `DELETE`
- `taxonomy_codes`: trigger rejecting `UPDATE` of `catalog_id` and `code`, and rejecting `DELETE`
- `outcome_taxonomy_mappings`: **no schema change** — no `taxonomy_catalog_id`, no `taxonomy_catalog_version` column is added

**EXACT_ALLOWED_VALUES_OR_INDEX_KEYS:** `UNIQUE(code, version)` on `taxonomy_catalogs`; `UNIQUE(catalog_id, code)` on `taxonomy_codes` — preserved unchanged; `UNIQUE(outcome_id, taxonomy_code_id)` on the mapping — preserved unchanged. **No new indexes** — the mapping→code→catalog path traverses primary keys on both hops, and the existing `idx_taxonomy_codes_catalog_id` already covers the reverse traversal.

**KEY_CONSTRAINTS:** the three pre-existing FKs are kept exactly as-is, all `NOT NULL`; `taxonomy_catalogs.version` is already `NOT NULL` — no new obligation is added; **no composite FK** — the target contains nothing PostgreSQL cannot express literally: one ordinary `UNIQUE` constraint and two `BEFORE UPDATE OR DELETE` triggers.

**IMMUTABILITY_RULE:** immutable are the columns that **carry the identity assertion** — `taxonomy_catalogs.code`, `.version`, `taxonomy_codes.catalog_id`, `.code` — and no row of either table admits DELETE. Mutable and auditable remain the **presentation/transcription** columns — `catalogs.name`, `.source_url`, `codes.label`, `.description`, `.sort_order` — because a mapping asserts "this outcome corresponds to element X of standard S version V," and fixing a transcription typo does not alter that assertion, while forbidding it would block a legitimate correction without any standard version having actually changed.

**VERSIONING_RULE:** a new version of an external standard is **a new catalog row**, never an in-place mutation; catalog version is data belonging to the external standard, not a Uellix-governed model, and does not enter `governed_model_registry`.

**RLS_PERMISSION_RULE:** unchanged. Catalogs and codes are global reference data — read for all org members, write only via the administrative seed; mappings keep their existing org-scoped policy unchanged.

**SOURCE_OF_TRUTH_TRACK:** DRIZZLE.

**BACKFILL_CLASS:** **BACKFILL_NOT_REQUIRED.** No column is created on the mapping, so there is nothing to backfill — not impossible, simply nonexistent as a question. No row of any of the three tables is modified by this migration.

**LEGACY_BEHAVIOR:** mappings created before the PC-01B boundary keep their row intact and resolve through the same chain they always have; they remain visible, legible, and available for consultation, context, and audit. The governance fact is stated without any new field: for a `pre_pc01b` mapping, the version the chain resolves to **today** is the catalog's *currently registered* version, and the system cannot attest that this was the version in force when the mapping was created, because the catalog row was mutable for the system's entire prior life and the seed updated it in place. This state is carried entirely by the existing `governance_regime` column (FIBDB-003) plus a presentation rule — **no substitute field is invented** to represent the absence. A `pre_pc01b` mapping is never presented as version-fixed in report, annex, export, or public surface; it is presented as a historical reference whose version is not attestable. A prospective version-fixed mapping is created as a **new governed mapping** against the current standard and version, with actor, date, and rationale — a decision made today, never a backfill.

**MIGRATION_DEPENDENCIES:** none. **ACTIVATION_DEPENDENCIES:** the immutability triggers and the uniqueness change require that FIBIU-32 has converted `scripts/seed-taxonomies.ts` from in-place `UPDATE` to insert-per-version **first** — with `(code, version)` uniqueness, a code-only lookup returns multiple rows once versions coexist, and with the triggers active the seed's two `UPDATE` statements fail outright; if hardening lands before the service change, **the seed breaks**. **MIGRATION_STAGE: E only** — no additive stage applies, since no new column exists to deploy ahead of the behavioral change; the uniqueness swap and both triggers are conductual and belong entirely to post-cutover hardening. ROLLBACK_CONSIDERATION: two triggers and one uniqueness constraint. Dropping the triggers and restoring `UNIQUE(code)` reverts the change, but **only while no standard has had a second version seeded** — once two versions of the same catalog coexist, `UNIQUE(code)` cannot be restored. This window is stated explicitly so it is not discovered late.

**FAIL_CLOSED_TEST:** (1) inserting a new catalog version alters no mapping, legacy or `pc01b`, and both versions coexist as distinct rows; (2) `UPDATE` on `taxonomy_catalogs.code`/`.version` is rejected by trigger; (3) `UPDATE` on `taxonomy_codes.catalog_id`/`.code` is rejected by trigger; (4) `DELETE` on either table is rejected by trigger; (5) correcting `catalogs.name` or `codes.label` is permitted and audited; (6) **no mapping can represent a mismatched code and catalog** — there is no column that could express it; (7) a `pc01b` mapping resolves deterministically to exactly one `(code, version, element)`; (8) no migration operation writes a version into any mapping; (9) a `pre_pc01b` mapping is never presented as version-fixed on any surface; (10) the non-certification disclaimer remains verbatim on all three surfaces. TRACK: DRIZZLE. OWNING UNIT: FIBIU-32.

**FIBDB-055** — `stella_governance_events`, NEW_TABLE. AUTH: V-09, V-17, F-14. CONTRACT: FIBC-030, FIBC-026. **Final normalized design (frozen at R3, superseding R2's `stella_application_events` name and its `applied_by`/`applied_at` columns).**

PURPOSE: durably preserve (a) the provenance V-09 requires when a person **explicitly applies** a Stella proposal, and (b) the trail V-17 requires when review was **omitted or unavailable**. Today neither exists: applying mutates only React state, and a run without Stella leaves no trace at all.

**Why the name and column set changed:** R2's `applied_by`/`applied_at` and the table name `stella_application_events` are both semantically false for two of the three event kinds — `review_unavailable` involves no application at all, and frequently has no human actor, originating instead from the system evaluating a capability flag, a missing provider key, or an exhausted quota. Naming a column "who applied" on an event with no application and often no actor misrepresents the event; the table name describing only one of three kinds is the same defect at the object level.

**Why this is a new Drizzle table rather than a revision of `stella_suggestion_decisions`:** that prepared, G2-applied table (its truncate trigger is present in the G2 dump) was designed for decisions on the contextual advisor's field-level suggestions, keyed by a client-assigned free-text `suggestion_key` — a different concept from the durable link this contract needs between a Stella **interaction** and the governed **object** a human applied it to. Revising an applied prepared table for a core product concept would require an external G2 gate for no benefit; a new Drizzle table has fewer moving parts and no external gate. `stella_suggestion_decisions` is therefore **`NO_COLLISION`**, remains intact, dormant, and untouched, and keeps its original contextual-suggestion semantics.

**TARGET_COLUMNS_OR_FIELDS — single event schema:** `id` (uuid PK); `organization_id` (uuid FK NOT NULL); `project_id` (uuid FK NOT NULL); `event_kind` (varchar NOT NULL); `occurred_at` (timestamptz NOT NULL); `actor_user_id` (uuid FK, nullable — obligation varies by kind); `stella_interaction_id` (uuid FK, nullable — obligation varies by kind); `object_type` (varchar, nullable — only on application); `object_id` (uuid, nullable — only on application); `section_id` (uuid, nullable — only on application); `omission_reason` (varchar, nullable — obligation varies by kind). `applied_by`/`applied_at` from the earlier design are retired in favor of the generic `actor_user_id`/`occurred_at`.

| --- | --- | --- | --- | --- |

**Explicit mapping to the existing governed error taxonomy — no open-ended strings:**

| `omission_reason` | Governed origin |
| --- | --- |
| `user_declined` | explicit human action to continue without running Stella |
| `capability_disabled` | `stellaCapabilityBlocker` returning `master_disabled` or `capability_disabled` |

**IMMUTABILITY_RULE:** append-only by trigger; a reverted application is a new event, never an UPDATE. **VERSIONING_RULE:** none — an event log. **RLS_PERMISSION_RULE:** org-scoped, SELECT for members, INSERT for the runtime; no UPDATE or DELETE, by absence of policy and by trigger. No event kind is ever exposed on the public surface.

**FAIL_CLOSED_TEST:** (1) applying registers the event with interaction, actor, object, and moment; if provenance cannot be persisted, the application is not saved; (2) not applying registers nothing and does not trigger the note; (3) the V-09 note appears exactly once, only with ≥1 `proposal_applied` event on the locked version; (4) never a per-section label; (5) a `review_unavailable` with `actor_user_id` NULL is valid; a `proposal_applied` with `actor_user_id` NULL is rejected; (6) `user_declined` on `review_unavailable` is rejected by CHECK; (7) `proposal_applied` with non-NULL `omission_reason` is rejected; (8) approval and lock remain possible without Stella, with the omission recorded and no degradation of the result; (9) UPDATE and DELETE are rejected. ## 6. Migration and Cutover Strategy

Two axes govern deployment, and they are orthogonal: the **backfill class** recorded per item in §4 governs what may be written during backfill (never fabricated history); the **deploy-safety stage** below governs *when* a change is safe to ship. A `SCHEMA_ONLY`-flavored item can still be behaviorally dangerous — e.g. a DELETE-rejecting trigger changes nothing about backfill but must not ship until its dependents exist — so staging is never inferred from backfill class alone.

### 6.1 Stages

**A · ADDITIVE_SCHEMA** — Tables, nullable columns, indexes, `NOT VALID` vocabularies, the model registry, the regime column. Also includes FIBDB-035 (the `audit_logs` INSERT policy), because it is *permissive* — it enables a write impossible today in a Drizzle-only environment and restricts nothing. Safety rule: the old runtime coexists unchanged; no constraint validates existing rows.

**B · SAFE_LEGACY_MARKING_AND_BACKFILL** — Only facts establishable **without invention**: `governance_regime='pre_pc01b'`; `report_version=1`; self-lineage; the `audit_logs.project_id` FK, validate-then-add; v1 evidence/proxy shells **with no invented values**; FIBDB-051 marks derived from already-persisted facts. Safety rule: every backfill must be derivable from an existing row; any default presented as a past fact is prohibited.

**C · DUAL_READ_OR_COMPATIBILITY** — The window in which the old runtime reads old fields and the new runtime reads new ones: the manual `readiness_score` coexisting with `readiness_assessments`; `verification_hash` coexisting with `report_public_disclosures`; `report_variant` coexisting with render-time representation selection. Safety rule: no new read may require a field the backfill left NULL.

**D · APPLICATION_CUTOVER** — New services become authoritative: eligibility composition, snapshot construction, Portfolio's approved population, Stella's contracts. No DDL. Precondition: A, B, and C complete and verified.

**E · FAIL_CLOSED_HARDENING** — Triggers, privilege revocations, restrictive RLS, immutability, explicit ordinary-DELETE rejection, mandatory prospective conditions, validation of the `NOT VALID` CHECKs scoped only to the `pc01b` regime. **Never before D** — hardening ahead of cutover leaves authoritative writes with no valid path.

**F · LEGACY_FINALIZATION** — Old fields and read paths become non-authoritative or read-only: retiring `verification_hash` as the public locator; the manual `readiness_score` stops feeding Portfolio and Stella; removing the unwired Stella fallback constants. Only once no live surface reads the old path.

### 6.3 Ordering of the externally-gated item relative to the Drizzle waves

FIBDB-053 is the baseline's only item with a human-external (G2) gate. Frozen ordering: (1) **wave 1** — the new prepared unit is authored and submitted to the G2 gate, in parallel with wave 1's Drizzle work; authorized early precisely because the gate is outside this plan's control; (2) **waves 1–2** — the G2 gate proceeds in parallel; no Drizzle unit depends on it; (3) **wave 3** — FIBIU-20 consumes it; if the gate has not resolved by the start of wave 3, FIBIU-20 stops, and with it FIBIU-24 and FIBIU-26 by transitive dependency; (4) **absolute prohibition** — no already-applied prepared unit is ever edited in place; a governed revision is always a new, versioned prepared unit registered in `db/prepared-package-order.ts`.

### 6.4 The three windows this sequencing closes

1. **Old runtime broken before the new one exists** — prevented because the entirety of stage A is additive and nullable, and the only early behavioral item (FIBDB-035) is permissive.
2. **New runtime operating without hardening** — prevented because E is a precondition of declaring cutover complete, and every behavioral item names its application prerequisite.
3. **Authoritative writes evading the new invariants** — prevented by the D→E order with an explicit requirement: between D and E, the new service is the *only* authoritative write path, and E converts that discipline into database enforcement. The window exists only as an application-layer discipline, not an absence of control, and it closes when E completes.

No stage suspends, recreates, or bypasses the append-only protections on runs, calculation line items, or audit logs.

## 9. Reports and Trust Baseline

### 9.1 Construction pipeline

```
approved eligible run  (FIBC-023 + FIBC-024, reviewer ≠ author)
  → report draft/version   (lineage + report_version, FIBC-031)
  → human narrative attestation, bound to content digest (FIBC-033)
  → complete snapshot build (FIBC-032)
  → atomic governed lock transaction, fail-closed
  → immutable version (DB trigger, not app check)
  → Executive Summary / Full Methodological renderings, snapshot-only (FIBC-035)
  → optional governed public verification + disclosure (FIBC-037)
```

Server-side preconditions at lock, all fail-closed and inside one transaction: the run has an approved review satisfying independence; run eligibility recomputes clean; every monetized outcome has approved evidence and a sufficiency determination; all filters are valued and justified; counterfactuals are present; sensitivity is `complete`; all material assumptions are resolved; every open Stella `high` finding is disposed; limitations are non-empty or an explicit, uncontradicted `no_material_limitations_identified` is recorded; every numeric value and reference in every section validates against the pinned run; the full snapshot builds. **No locked rendering may query live methodology tables for governed content.**

### 9.2 Version, snapshot, lock

Report version lineage (FIBC-031) is a simple increasing sequence within a lineage; each locked version is an immutable artifact declaring its run, `run_version`, methodology/engine versions, locking actor and date, and snapshot identity. The snapshot (FIBC-032) is the complete, self-sufficient methodological package — see §3's full field enumeration — captured atomically with validation and the transition to `locked`, failing closed if the package cannot be built in full. Lock (FIBC-033) preserves and extends the existing narrative-attestation lock, adding: attestation bound to the concrete report/draft identity, run, actor, and date, never reusable across a material content change; reference authority restricted to eligible evidence at its concrete used version. Limitations (FIBC-034) are a mandatory, non-substitutable declaration distinct from the general notice.

### 9.3 Representations

`Executive Summary Report` and `Full Methodological Report` (FIBC-035) are the two mandatory official representations, both rendered exclusively from the same immutable snapshot with identical figures, methodology, versions, decisions, scope, and limitations. The pre-existing `audit` and `methodological` variants are retained as `LEGACY_ALIAS` pointing to the Full Methodological Report; `funder` is retained as an `OPTIONAL_PRESENTATION_PRESET`. Representation is a render-time selection over any locked version — it creates no new version, requires no new run, and is not itself a methodological decision. The F-15 notice (FIBC-036) accompanies every representation in product, PDF, print, and the public surface; the single V-09 transparency note appears once, only when a `proposal_applied` Stella-governance event exists on the locked version.

### 9.4 Public verification

`PUBLIC_REPORT_VERIFICATION_POLICY_v1.0.0` (FIBC-037) governs public disclosure: disabled by default per report version, activated only by an explicit authorized act on a concrete locked version; a fixed, non-toggleable `verification_core`; two independently-false-by-default optional bundles; a separately governed `public_document` selector defaulting to `none`; V-26 sensitivity classification has absolute fail-closed precedence over activation or modification; the public read model is built exclusively from the snapshot and the disclosure object; the locator token is opaque, high-entropy, and never conflated with an integrity digest; revocation is a prospective, audited human act that leaves the snapshot, digest, content, and history untouched. Reports classified `legacy_locked_without_pc01b_snapshot` are permanently ineligible.

## 10. Portfolio Baseline

The authoritative aggregate (FIBC-038) is computed exclusively from, for each member project, **the most recent approved eligible run** — never simply the latest calculated run. The formula is preserved exactly as `Σ net social value / Σ investment` over the same universe for numerator and denominator; it is never a simple or weighted average, sum, median, or other aggregation of individual project ratios, and an excluded run contributes to neither the numerator nor the denominator. Projects with no approved run remain visible, excluded with an explicit, distinct reason, and counted in the coverage figure the interface must present. A later, ineligible run may be surfaced as clearly differentiated operational information but never substitutes for, or blends with, the last approved run in the aggregate. **A locked report is not a prerequisite for a run to participate** — methodological approval of the run is the applicable requirement, decoupling Portfolio eligibility from the reporting pipeline entirely. When no eligible run exists, or aggregate investment is zero, absent, or methodologically invalid, **no authoritative portfolio SROI is emitted**, and the impossibility is represented explicitly rather than silently defaulting to zero or omission. Descriptive statistics over individual ratios (median, distribution, range) are permitted under their own correct names and must never be confused with, or presented alongside, the consolidated ratio without clear differentiation. Descriptive readiness statistics use the canonical NPDD-01 readiness score with coverage; the manual `readiness_score` is dropped as a Portfolio input entirely. The journey gap — Portfolio built but unreachable from `Sidebar.tsx`, `TopBar.tsx`, and the dashboard — is closed as part of the same unit (FIBIU-27) that fixes the population predicate, since restoring navigation to a component whose data is still wrong would surface the defect more visibly rather than fixing it.

## 11. Legacy Transition Baseline

`legacy_non_authoritative` handling (FIBC-042) governs every pre-PC-01B object, run, decision, evidence item, proxy, review, and report where compliance with a new gate cannot be demonstrated from genuinely persisted, verifiable information. The governing principle, restated as the single rule every backfill in §4 and §6 obeys: **missing history is never completed by inference, by a default posing as a past fact, by speculative reconstruction, or by a fabricated retroactive decision.** The classification is prospective governance, not a retroactive claim that the historical artifact was invalid when created; content is preserved intact, remains consultable, and remains available for context reconstruction and audit. A legacy object cannot, by itself, satisfy a new gate, produce a new authoritative run, contribute to an authoritative Portfolio aggregate, support a new approval, or enable new public verification.

Per-domain legacy regimes, each cross-referenced to its owning database item: historical runs keep `NULL` methodology/engine/build identity permanently (FIBDB-001, `IMPOSSIBLE_TO_BACKFILL`) and are never retro-converted; the manual `readiness_score` survives as historical data only and stops feeding Stella, Portfolio, and canonical surfaces (FIBDB-016); text evidence with a hash but no content becomes `legacy_content_unverifiable` (FIBDB-005) — new content is registered as a **new evidence version**, never presented as a byte-identical reconstruction; historically `approved` proxies lacking full provenance/actor/version/rubric become `legacy_non_authoritative_for_new_runs` (FIBDB-006), requiring a new version through the full cycle with no automatic approval transfer; historical self-approvals are preserved exactly and never satisfy V-04 (FIBDB-040, FIBDB-051's `legacy_self_approved_review`); reports locked before the V-07 snapshot become `legacy_locked_without_pc01b_snapshot` (FIBDB-024), permanently ineligible for V-31 public verification, with no retrospective snapshot construction; taxonomy mappings created before the boundary keep resolving through their unchanged FK chain and are never presented as version-fixed — no substitute field is invented to represent that absence (FIBDB-054, final normalized design, §4).

`legacy_class` (FIBDB-051) makes every one of these regimes verifiable by machine, derived exclusively from already-persisted facts (`content IS NULL`, `snapshot_identity IS NULL`, `reviewer_id = calculated_by`, `methodology_version IS NULL`) — never from inference. Work in progress may continue as preparation but must satisfy the new requirements before acquiring authoritative status; prospective completion by an authorized person is always **a new decision carrying today's actor and date**, never a backfill. There is no grandfathering and no destructive degradation. Nothing in this baseline authorizes suspending, disabling, bypassing, or recreating the append-only protections on runs, calculation line items, or audit logs — this holds even where a legacy regime is being established.

`LEGACY_SPECULATIVE_BACKFILLS = 0` is a standing property of every backfill this baseline authorizes (verified per-category in §17), not a count computed once at freeze time.

## 14. Acceptance Test Baseline

Required families, each with its critical invariant and test level (`U`nit / `I`ntegration / `DB` / `C`ontract / `E2E`):

- **Deterministic calculation (U)** — same inputs ⇒ byte-identical result via decimal.js, no float drift.
- **Proxy governance (I+DB)** — an unapproved version never reaches the engine on the server path.
- **Material-change invalidation (DB)** — no window where `approved` survives a material change.
- **Evidence lifecycle (U+DB)** — five states only; `rejected`/`archived` never satisfy.
- **Evidence erasure (DB+I)** — ordinary DELETE fails explicitly, never 0 rows; tombstone written; derivatives swept; docs/19 not activated.
- **Evidence sufficiency (U)** — never inferred from count, status, or score.
- **Materiality (U)** — the 1–5 score never auto-classifies.
- **Counterfactual (U)** — supported `0` vs. unknown distinguished.
- **Assumptions (U)** — free text never auto-converts.
- **Causal chain (U)** — `activity→outcome` rejected; a monetized outcome without a chain is ineligible.
- **Readiness (U)** — 46 criteria, ten dimensions at 10% each, a governed `not_applicable` counts as satisfied, readiness never gates approval.
- **Sensitivity (U+I)** — the uniform ±10pp is absent; completeness gate holds; scenarios use the same engine.
- **Run eligibility (I)** — every enumerated reason is reachable; the run row stays unmutated.
- **Segregation of duties (I)** — `reviewer_id = calculated_by` rejected server-side.
- **Run immutability (DB)** — UPDATE/DELETE raise.
- **Report snapshot (I)** — the locked render issues **zero** queries against live methodology tables.
- **Report versioning (I)** — a post-lock change yields a new version.
- **Report lock (I+DB)** — fails closed on each precondition; the transaction is atomic.
- **Both report variants (C)** — identical figures from one snapshot.
- **Public verification (I+E2E)** — default off; the core is all-or-nothing; sensitivity precedence holds; the token is never a digest; legacy is ineligible; revocation is prospective.
- **Portfolio Σ/Σ (U+I)** — approved-only population; never averages ratios; no ratio on zero investment.
- **Stella `requires_human_review` (C)** — `false`/absent rejected, never coerced.
- **Stella citations (C)** — an out-of-range index, alias, or leaked token invalidates the whole response.
- **Stella abstention (C)** — structured, per-claim, present in the **live** roles.
- **Stella untrusted data (C)** — embedded instructions are inert.
- **Audit-before-delivery (I)** — an audit failure withholds the output entirely.
- **Stella draft/apply (I)** — no auto-persistence; autosave cannot persist an unapplied proposal.
- **High-risk disposition (I)** — an open finding blocks approval and lock.
- **Tenant isolation (I+DB).**
- **RLS (DB).**
- **Legacy behavior (I)** — no fabricated backfill; legacy is ineligible for new gates.
- **No docs/19 activation (C)** — the flag stays false and no grounding database object is created.
- **Taxonomy identity (DB)** — a version change alters no historical mapping; a mismatched code/catalog pair is unrepresentable, not merely forbidden (FIBDB-054).
- **Stella governance events (DB)** — the per-kind CHECK obligations of FIBDB-055 hold; `user_declined` is never coded as `review_unavailable`.

**Currently absent and required by this baseline:** segregation-of-duties, report snapshot completeness, report lock, report versioning, public verification, evidence erasure, sensitivity, assumptions, counterfactual, materiality, proxy rubric. **Present and to be preserved without relaxation:** Portfolio Σ/Σ (`lib/portfolios/analytics.test.ts`), append-only (`tests/append-only-error.test.ts`), RLS (`tests/database-runtime-rls.test.ts`), Stella anti-regression suites, report-variant tests.
